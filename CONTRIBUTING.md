# CONTRIBUTING.md

## Руководство по вкладу и стилю кода

Этот документ описывает правила оформления кода и стиль комментариев для проекта. Цель — единообразие и понятность: комментарии должны выглядеть так, будто их написал автор проекта.

### Общие принципы
- Код должен быть ясным и компактным. Предпочтительны простые функции с одной ответственностью.
- Убирайте дублирование, выносите повторяющийся код в приватные вспомогательные методы.
- Избегайте избыточных комментариев: комментируем почему, а не что (если код не самодокументируемый).

### Стиль комментариев
- Язык комментариев — русский.
- Комментарии короткие, в первом лице единственного или повелительном наклонении (например: "Загружаю студентов", "Скрыть столбец с ID").
- Использую ясные метки для задач: `// TODO:` и `// FIXME:`. После метки кратко указываю причину и приоритет.
- Многострочные комментарии допустимы для сложной логики, но стараюсь их сокращать.

Примеры:
```csharp
// Загружаю список студентов в dataGridView1
private void LoadStudentsToGrid() { ... }

// Скрываю служебный идентификатор
idCol.Visible = false;

// TODO: вернуть поиск по ID, когда добавлю индекс в БД
```

### Именование
- Следую существующей кодовой базе: PascalCase для методов и типов, camelCase для локальных переменных и полей с `_` для приватных полей (`_dbPath`).

### Форматирование
- Соблюдаю `.editorconfig` правила отступов и длины строк. Если `.editorconfig` отсутствует, использую 4 пробела для отступа.

### Рефакторинг комментариев
- При массовой замене комментариев: заменяю длинные/объясняющие формулировки на короткие фразы от первого лица или в императиве.
- Не изменяю семантику кода без явного согласия.

## Процесс внесения изменений
1. Создаю ветку `refactor/comments-and-simplify`.
2. Вношу изменения по файлам или пакетно, оставляю мелкие коммиты с пояснениями.
3. Запрашиваю PR для обзора.

## Правила переформулирования текстовых разделов ПЗ и аннотаций

Эта секция описывает требования к адаптации и переформулированию текстовых материалов (аннотации, разделов пояснительной записки, примеров), которые добавляются в проект или запрашиваются ревьюером.

Цель: получать тексты, оформленные человеческим, понятным русским языком, без потери технической точности и сохраняя объём исходного материала.

Правила:
- Язык — русский. Сохранять академический стиль, но писать понятным языком (избегать излишне громоздких оборотов).
- Объём — близкий к исходному: итоговый текст не должен быть существенно короче или длиннее оригинала (погрешность ±15%).
- Структура — сохранять логические блоки и заголовки оригинала. Если нужно, добавлять подзаголовки для ясности.
- Тон — официально-деловой, в третьем лице или безлично, если пример этого требует; в дидактических примерах — можно использовать императив.
- Терминология — сохранять названия таблиц, полей, процедур и функций проекта без перевода (например: `STUDENTS`, `GET_FULL_JOURNAL`, `PHOTO`).
- Технические вставки (SQL, имена процедур, имена методов) оформлять в кодовых блоках и не упрощать смысл.
- При адаптации примеров из другой темы — заменять сущности на соответствующие сущности текущего проекта (ученик, класс, предмет, оценка, достижение), сохранять логику и объём.
- Формат вывода — Markdown. Диаграммы — mermaidJS (если требуется), таблицы — Markdown-таблицы.
- Комментарии и пояснения внутри текста — короткие, по возможности в императиве.

Процесс работы с материалом:
1. Пользователь присылает фрагмент текста (аннотацию, раздел ПЗ или пример).
2. Я возвращаю адаптированную версию этого фрагмента в Markdown, соблюдая правила выше.
3. При необходимости выполню 1–2 доработки по комментариям пользователя.

Примеры применения правил:
- "Перепиши аннотацию" ? отдаю аннотацию тем же объёмом, понятным языком, с упоминанием используемых процедур/таблиц.
- "Адаптируй пример раздела из другой темы" ? заменяю сущности и SQL на эквиваленты проекта, сохраняю структуру и объём.

Если нужно изменить стиль (более формально, короче, для непрофессиональной аудитории) — укажите явно в запросе.
